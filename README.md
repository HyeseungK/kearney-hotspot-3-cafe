# kearney-hotspot-3-cafe

서울의 다음 핫플레이스를 찾아라: 스페셜티 카페 편. 향후 3년 안에 뜰 서울 상권 3곳과 1순위 상권의 매장 컨셉을 제안하는 웹사이트입니다. 웹사이트 본체는 `index.html` 한 파일입니다. 배포 주소: https://hyeseungk.github.io/kearney-hotspot-3-cafe/

## 1. 조원별 역할

| 이름 | 역할 |
|------|------|
| 김혜승 | API 연동 지표 분석, 카페 컨셉 디테일 고안 |
| 김기완 | 지표 기반 후보 검증, 카페 기본 컨셉 제안 |

## 2. "뜬다"의 정의 (한 줄)

> 개인 카페가 서울 상위권 속도로 늘고, 20~30대 유동 비중이 높고 오르며, 아직 성수·홍대만큼 포화되지 않았고, 서울시 상권변동지표가 다이나믹·확장인 상권.

## 3. 사용한 프롬프트 전체

Claude Code(Claude)에 입력한 프롬프트를 시간 순서대로 가공 없이 붙였습니다. 이 과제와 무관한 이전 요청(카카오 실적 분석 등)은 제외했습니다. 프롬프트에 포함된 API 키는 `[API 키 생략]`으로 바꿨습니다(그 외 수정 없음).

## 1. 작업 시작 전 규칙 (반드시 지킬 것)

### 1-1. 데이터 정직성 (평가 기준 02 "근거가 사실인가"와 직결)
- **숫자를 지어내지 마라.** 모든 수치는 출처(기관·문서명·URL·조회 시점)가 있어야 한다.
- 실제로 확인한 값은 "확인", 추정·보간한 값은 "추정(방법 한 줄)"로 사이트에 명시한다.
- 데이터를 못 구했으면 못 구했다고 쓰고, 대체 근거(기사, 공개 통계, 현장 관찰 가능한 정성 근거)를 쓴다. 그럴듯한 가짜 수치는 감점이 아니라 **실격 사유**로 취급한다.
- 참고 데이터 (미션 문서에 명시된 것): 서울시 상권분석서비스, 서울 열린데이터광장 Open API, 그 외 공개된 통계·기사·SNS 데이터.
- **서울 열린데이터광장 Open API가 1차 데이터 출처다.** 호출·키 처리·수집 방식은 §1-4를 따른다. 키는 사람에게 요청하고, 코드·README·커밋에 노출하지 마라. 사이트에는 가공된 결과값만 넣는다.

### 1-2. 사람에게 확인받을 것 (임의로 진행 금지)
- 다음 항목은 반드시 사람의 명시적 승인 후 실행: GitHub 저장소 생성, `git push`, GitHub Pages 설정 변경, 파일 다운로드, 계정 정보·토큰 입력.
- 사람이 부재일 수 있으니, 승인이 필요한 시점이 오면 **준비를 끝내 놓고 "이것만 승인해 주세요"라고 한 번에 묻는다.**

### 1-3. 스킬·도구 사용 지침
- 시작하자마자 사용 가능한 스킬/플러그인 목록을 확인하라 (`/skills` 또는 동등한 명령). 아래 용도에 맞는 것이 있으면 적극 사용한다.
  - 웹 리서치·출처 수집 (web search / fetch)
  - 프론트엔드 디자인 / 웹페이지 제작 스킬 (프론트엔드 디자인, HTML 아티팩트 계열)
  - 데이터 시각화·차트 스킬 (차트 색상·접근성·레이아웃 가이드)
  - 슬라이드·문서 스킬은 이번 과제에 **불필요**하다 (산출물은 웹사이트)
- 서브에이전트를 쓸 수 있으면 **리서치를 병렬화**하라 (아래 3단계의 후보 상권별 조사를 에이전트 1개씩 배정). 단, 최종 판단과 사이트 통합은 메인 에이전트가 직접 한다.
- 작업 폴더는 `kearney-hotspot-{조번호}-cafe/` 하나만 쓴다. 중간 메모는 `notes/` 하위에 두고 **배포 전에 `notes/`는 제외하거나 지운다** (루트에는 `index.html`, `README.md`만 남긴다).

### 1-4. 서울 열린데이터광장 Open API 활용 지침 (필수)

이 과제의 핵심 근거 데이터는 **서울 열린데이터광장(data.seoul.go.kr) Open API**로 직접 수집한다. 기사·SNS는 보조 근거다. 아래 내용은 공식 안내 페이지에서 확인한 사실과, 실행 중에 **직접 검증해야 할 항목**을 구분해 적었다.

**(a) 확인된 사실**
- 요청 URL 형식: `http://openapi.seoul.go.kr:8088/{KEY}/{TYPE}/{SERVICE}/{START_INDEX}/{END_INDEX}/{추가 파라미터}`
  - TYPE은 `xml`, `xmlf`, `xls`, `json` 중 선택 → **`json` 사용**
  - SERVICE명은 **대소문자를 구분**한다. 앞 5개 파라미터는 순서를 바꾸면 안 된다.
  - 1회 호출당 최대 **1,000건**. 그 이상은 START/END 인덱스를 나눠 반복 호출(페이징)한다.
  - `sample` 키로는 1~5건만 조회된다. 구조 확인용으로만 쓰고, 실제 수집은 발급받은 인증키로 한다.
- 인증키는 열린데이터광장에서 "일반 인증키"를 신청해 발급받는다. **키 발급은 사람이 직접 한다.** (너는 키를 만들거나 대신 신청하지 않는다.)
- 우리 과제의 공식 참고 데이터인 **상권분석서비스(서울신용보증재단 제공)** 데이터셋이 열린데이터광장에 올라와 있다. 확인된 항목:
  - 서울시 상권분석서비스(**추정매출-상권**) — 분기 갱신. 추정매출액 = 카드결제금액 ÷ 보정비율
  - 서울시 상권분석서비스(**점포-상권배후지**) — 월 갱신. 점포 수·개업/폐업·프랜차이즈 정보
  - 서울시 상권분석서비스(**직장인구-행정동**) — 분기 갱신
  - 상권분석서비스(golmok.seoul.go.kr)가 쓰는 그 밖의 지표: 점포(개·폐업률, 생존율), 생활인구, 길단위 유동인구, 임대시세(환산임대료), 상권활성화지수(매출·인프라·가맹점·인구·금융), 공실률, 소득분위, 교통카드 승하차, 주거인구
  - 정의: 개/폐업률 = (기간 내 개업·폐업 점포 수 ÷ 전체 점포 수) × 100, 환산임대료 = (보증금 × 12%) ÷ 12 + 월세
- **데이터 범위 주의:** 추정매출-상권은 2024년 표준 상권 경계가 바뀌어서 **2021년 이후 데이터만** 제공된다(2026-07 공지). 따라서 아래 백테스트 설계에 반영해야 한다.

**(b) 실행 중 반드시 직접 확인할 것 (추측 금지)**
- 각 데이터셋의 **SERVICE명과 응답 필드명은 데이터셋 페이지의 "Open API" 탭**에서 확인한다. 기억이나 추측으로 SERVICE명을 쓰지 마라. 대소문자 하나만 틀려도 호출이 실패한다.
- 사용할 데이터셋마다 `sample` 키로 `1/5` 호출을 먼저 해서 **응답 JSON 구조와 필드명, 기준 시점(분기/연월) 필드**를 `notes/api-catalog.md`에 기록한 뒤 본 수집에 들어간다.
- 응답의 `RESULT.CODE`를 확인하라. `INFO-000`이 정상이다. `INFO-200`(데이터 없음), 인증키 오류, 호출 제한 오류가 나오면 원인을 기록하고 사람에게 보고한다.
- 지표 후보(점포 순증가, 폐업률, 생활인구 변화, 임대료 등)가 열린데이터광장에서 실제로 제공되는지는 위 Open API 탭에서 확인한 뒤에 지표로 확정한다. 제공되지 않는 지표를 정의에 넣지 마라.

**(c) 인증키 처리**
- 사람이 발급받은 키를 **환경변수 `SEOUL_API_KEY`**로 받는다. 코드에 하드코딩하지 않고, `.env`는 `.gitignore`에 넣는다. README, 커밋, `index.html`, 프롬프트 로그 어디에도 키가 찍히면 안 된다.
- 키를 아직 못 받았다면: `sample` 키로 구조 파악과 수집 스크립트 작성까지 끝내 놓고, 사람에게 "키를 `SEOUL_API_KEY`에 설정해 주세요"라고 요청한다. 그때까지 임의의 대체 수치로 사이트를 채우지 마라.

**(d) 수집 방식: 브라우저가 아니라 사전 수집 스크립트로**
- 최종 사이트는 GitHub Pages(HTTPS) 정적 페이지다. `openapi.seoul.go.kr:8088`는 HTTP라서 **페이지에서 직접 호출하면 혼합 콘텐츠로 막히고**, 키도 노출된다. 따라서:
  1. `scripts/fetch_seoul.py`(또는 Node)로 **로컬에서** API를 호출해 원본 JSON을 `notes/raw/`에 저장한다. (페이징 + 호출 사이 짧은 대기 + 실패 재시도)
  2. `scripts/build_metrics.py`로 지표를 계산해 **가공 결과(작은 JSON)** 만 만든다.
  3. 그 결과를 `index.html` 안에 `<script>const DATA = {...}</script>`로 **인라인 삽입**한다. 사이트는 API 없이 독립 동작해야 한다.
- 원본(raw)은 저장소에 올리지 않는다. 대신 README에 `데이터셋명, SERVICE명, 호출 기준일, 사용 필드, 가공식`을 적어 재현 가능하게 한다.
- 사이트의 출처 섹션에 각 데이터셋의 **이름 · 제공기관(서울신용보증재단 등) · 기준 분기/월 · 조회일**을 표기한다.

**(e) 스크리닝 설계 (API로 가능한 방식)**
1. 분석 단위 결정: 상권 단위(상권분석서비스의 상권)로 갈지 행정동으로 갈지, 데이터셋마다 단위가 다르다. 단위가 서로 다르면 지표를 하나로 합치기 전에 **공통 키(행정동 또는 상권코드)로 매핑**하고, 매핑 방법을 사이트에 한 줄로 밝혀라.
2. 서울 전역 전수 수집 → 지표 계산 → 이미 뜬 곳 제외 필터(예: 매출·임대료 수준이 이미 높은 상권) → 상위 후보 5~8곳.
3. 후보마다 **카페(커피-음료 업종) 한정** 지표로 다시 계산한다. 업종 코드/업종명 필드는 Open API 탭에서 확인한다.
4. 최종 3곳은 API 수치 + 현장 맥락(기사, 개발 호재 등)을 합쳐 결정한다. 수치와 맥락이 충돌하면 충돌 자체를 사이트에 기록한다.

**(f) 백테스트 설계 시 주의**
- 상권분석서비스 데이터는 2021년 이후만 안정적으로 제공되므로, 백테스트 대상은 **2021년 이후에 실제로 뜬 상권**이거나, 더 긴 시계열을 가진 다른 데이터(예: 열린데이터광장의 업종별 인허가 이력 데이터가 있는지 검색해서 **존재 여부부터 확인**)로 보완한다.
- 어느 쪽이든 "내 지표를 뜨기 전 시점의 데이터에만 적용했을 때" 감지됐는지를 보여줘야 한다. **뜬 이후의 데이터를 섞으면 검증이 아니라 사후 설명**이 된다. 사용한 기간을 사이트에 명시한다.
- 가능한 시계열이 짧으면 짧다고 쓰고, 한계로 기록한다.

## 2. 평가 기준 — 모든 의사결정의 기준표

아래 5개 + 가산점 1개로 채점된다. 작업할 때마다 이 표로 돌아와서 확인하라.

| # | 기준 | 심사 질문 | 이걸 만족시키는 방법 |
|---|------|----------|--------------------|
| 01 | 지표 설계의 논리성 | 지표가 논리적으로 명확하고 정합성이 있는가 | 지표마다 "왜 이 지표가 상권이 뜨는 신호인가"를 인과로 설명. 선행 지표와 후행 지표를 구분하고 서로 모순되지 않게 구성 |
| 02 | 근거의 구체성 | 명확한 근거가 있고, 그 근거가 사실인가 | 수치+출처+기준 시점. 확인/추정 표기. 지어낸 숫자 금지 |
| 03 | 인사이트 | 클라이언트가 "와우!"할 만한가 | 통념을 뒤집거나 남들이 안 보는 신호 하나를 찾아 헤드라인으로 올림 |
| 04 | 컨셉의 정합성 | 상권 분석 → 타겟 → 메뉴 → 차별성까지 일관되게 이어지는가 | 상권에서 관찰된 사실 하나가 타겟을 정하고, 타겟이 메뉴를 정하고, 메뉴가 차별성이 되는 **한 줄 인과 사슬**을 사이트에 시각화 |
| 05 | 전달력 | 웹사이트가 30초 안에 핵심을 전하는가 | 첫 화면(스크롤 없이)에 결론 전부 노출. 본문은 근거 확인용 |
| 가산점 | BONUS | 제안 상권을 알리는 모션 그래픽 영상이 존재하는가 | 5단계 참조. 필수 요건을 다 끝낸 뒤에만 착수 |

**우선순위 원칙:** 필수 5개 요건(§3) 충족 → 30초 전달력 → 인사이트 → (남는 시간에) 모션 그래픽.

## 3. 사이트에 반드시 포함할 5가지 (미션 필수 요건)

누락 시 미완성으로 간주된다. 각 항목에 대응하는 섹션을 사이트에 만들어라.

**① "뜬다"의 정의**
- 상권이 뜨는 신호를 판단할 **지표 3개 이상** + **각 지표를 고른 이유**.
- 그리고 README에 쓸 **"뜬다"의 정의 한 줄** (예: "개인 운영 카페의 순증가가 N개월 연속 이어지고 20~30대 유동인구가 늘되 임대료는 아직 서울 평균 이하인 상권").
- 지표 설계 가이드: 서로 다른 성격의 신호를 섞어라. 예시 풀(그대로 쓰지 말고 데이터 가용성에 맞춰 선택):
  - 수요 신호: 20~30대 유동·거주·직장 인구 변화, 주말/야간 유동 비중
  - 공급 신호: 개인 운영 카페·로스터리·독립 매장의 순개업(개업-폐업), 프랜차이즈 비중 변화
  - 선행 vs 후행: **임대료·권리금 급등은 후행**(이미 뜬 뒤). 선행 지표(개인 매장 유입, 정성적 SNS 언급 증가, 생활인구 변화, 개발·교통 호재)를 중심에 두어라.
  - 안전장치: 생존율(폐업률), 임대료 수준(아직 진입 가능한가)
- 지표마다 `정의 / 데이터 출처 / 왜 뜨는 신호인가 / 한계` 4개 항목을 갖춰라.

**② 검증 (백테스트)**
- **과거에 뜬 상권 1곳**에 내 지표를 적용해 "그때 미리 잡아낼 수 있었는가"를 보여라. (예: 성수, 연남 등 이미 뜬 곳 중 과거 시점 데이터가 확보되는 곳 1개)
- 형식: "뜨기 N년 전 시점의 지표값 → 우리 기준이면 감지됐는가(예/아니오/부분적)" 시계열 표나 차트 하나.
- **못 잡아낸 부분이 있으면 숨기지 말고 쓰고**, 지표를 보완한 내용을 기록하라. 정직한 검증이 점수가 높다.
- 과거 시점 데이터가 부족하면 가능한 범위(예: 개업 점포 수, 기사 타임라인)로 대체하고 한계를 명시.

**③ 추천 상권 3곳**
- 각 상권마다: 근거 데이터(지표별 수치+출처), **왜 지금인가**, 3곳 간 비교.
- **1순위를 고른 이유**를 명시적으로 기술 (3곳 비교표 + 한 문단 판단 근거).
- **이미 뜬 곳은 제외.** 후보군에서 성수·연남 같은 이미 포화된 상권을 걸러낸 기준도 한 줄로 밝힐 것. (한 줄 정의에서 "아직 임대료가 서울 평균 이하" 같은 조건이 이 필터 역할을 하면 논리가 깔끔하다.)
- 후보 발굴 방법: 서울 전역(또는 구 단위)을 정의한 지표로 **스크리닝 → 상위 후보 5~8곳 → 심층 조사 → 최종 3곳**. 상권 이름을 직감으로 먼저 정하고 데이터를 끼워 맞추지 마라. 순서가 반대면 논리성 점수가 깎인다.

**④ 매장 컨셉 (1순위 상권 대상)**
- 4개 항목을 모두 포함: **타겟 고객 / 메뉴 구성 / 차별성 / 상권 적합성**.
- 정합성 사슬: `상권에서 관찰한 사실 → 타겟 → 메뉴 → 차별성`이 한 줄로 이어지게 하고, 사이트에 화살표 다이어그램으로 보여라.
- 스페셜티 커피 특성을 반영: 원두(싱글 오리진/블렌드, 로스팅 방식), 추출 방식(핸드드립·에스프레소·콜드브루 등), 공간 경험(좌석 구성, 체류 방식, 바 구조, 시그니처 요소), 객단가·체류 시간 가정.
- 메뉴·가격은 시장 조사 근거(주변 경쟁 카페 가격대 등)를 붙여라. 차별성은 "그 상권의 기존 카페들이 못 채우는 빈틈"으로 정의한다 (경쟁 공급 분석 필요).

**⑤ 리스크 한 가지**
- "이 추천이 틀릴 수 있는 이유"를 **정확히 한 가지**, 가장 치명적인 것으로.
- 어떤 신호가 나타나면 추천을 철회해야 하는지(조기 경보 지표)까지 한 줄 덧붙이면 가산 효과.

## 4. 사이트 설계 지침 (전달력 = 30초 규칙)

**핵심 원칙: 첫 화면(스크롤 없이 보이는 영역)만 읽어도 결론이 전달돼야 한다.**

**첫 화면(히어로)에 반드시 있어야 할 것**
- 한 줄 결론 (예: "3년 뒤 스페셜티의 다음 자리는 ○○입니다")
- 추천 상권 3곳 (1순위 강조) — 이름 + 한 줄 이유
- "뜬다"의 정의 한 줄
- 1순위 매장 컨셉 한 줄 요약
- (있다면) 모션 그래픽이 여기서 재생

**이후 섹션 순서 (스크롤 시 근거 확인용)**
1. 히어로 요약
2. "뜬다"의 정의 + 지표 3개+ (이유 포함)
3. 검증: 과거 상권에 적용한 결과
4. 상권 3곳 비교 (표 + 차트) → 1순위 선정 이유
5. 1순위 매장 컨셉 (타겟→메뉴→차별성→상권적합성 사슬)
6. 리스크 한 가지 + 조기 경보 신호
7. 출처·데이터 기준 시점·확인/추정 구분
8. 팀 소개(Kearney 팀, 조번호)

**디자인 요구**
- 모바일 폭에서도 깨지지 않을 것 (가로 스크롤 없음). 라이트/다크 대응은 선택.
- 스페셜티 커피 무드에 맞는 톤 (절제된 색, 타이포 위계 명확, 과한 장식 금지). 한글 가독성 우선 (웹폰트는 Google Fonts만 허용, 또는 시스템 폰트).
- 차트는 SVG/Canvas 직접 구현 또는 CDN(cdnjs) 라이브러리. 색 대비와 범례를 명확히. 차트 하나당 메시지 하나(제목에 결론을 쓴다: "A상권의 개인 카페 순증가는 3년 연속 상승").
- 문장은 짧게. 숫자는 크게. 설명 문단보다 도식·표를 우선.
- 외부 이미지 핫링크 금지(깨질 위험). 이미지가 필요하면 SVG로 직접 그리거나 생략.
- `index.html` 단일 파일. 파일 크기는 가볍게 유지.

**완성 후 30초 테스트 (스스로 수행)**
브라우저에서 열어 스크롤 없이 처음 30초 동안 읽는다고 가정하고 질문에 답이 보이는지 확인: ① 어디를 추천하나? ② 왜 지금인가? ③ 뭘 팔 건가? 셋 중 하나라도 안 보이면 히어로를 고쳐라.

## 5. 가산점: 모션 그래픽 (선택, 필수 요건 완료 후)

"제안 상권을 알리는 모션 그래픽 영상이 존재하는가"

- 필수 5요건과 30초 전달력이 끝난 뒤, 남는 시간이 10분 이상일 때만 착수.
- 구현 방식(영상 파일이 아니어도 됨): **같은 페이지에 포함된 CSS/SVG/JS 애니메이션 시퀀스** (10~20초 루프). 예: 서울 구 경계 윤곽 → 3개 상권이 차례로 점등 → 1순위가 확대되며 핵심 지표 숫자가 카운트업 → 상권명과 한 줄 컨셉 노출.
- 또는 별도 영상 파일(mp4/webm)을 만들 수 있으면 `assets/`가 아니라 **루트나 하위 폴더에 두고 `index.html`에서 상대경로로 연결**. 단, 파일 용량과 GitHub 업로드 제한(단일 파일 100MB)에 주의.
- 자동재생 시 음소거, 사용자가 멈출 수 있는 컨트롤 제공, `prefers-reduced-motion`에서는 정지 상태로 대체.
- 모션은 장식이 아니라 **정보 전달**(상권 위치, 변화량)에 쓸 것.

## 7. 제출물 상세

### 7-1. 저장소
- 이름 규칙: **`kearney-hotspot-{조번호}-cafe`** (예: `kearney-hotspot-3-cafe`)
- 공개 범위: **Public**
- `index.html`은 **맨 위 폴더(루트)**에 둔다. (하위 폴더에 두면 Pages가 안 열린다.)

### 7-2. README.md 필수 내용 (3가지)
```markdown
# kearney-hotspot-{조번호}-cafe

## 1. 조원별 역할
| 이름 | 역할 |
|------|------|
| {이름} | {예: 리서치 / 지표 설계 / 사이트 제작 / 컨셉 / 배포} |

## 2. "뜬다"의 정의 (한 줄)
> {한 줄 정의}

## 3. 사용한 프롬프트 전체
{Claude Code에 입력한 프롬프트를 시간 순서대로, 가공 없이 전부 붙여넣기.
 이 가이드 문서 전문 + 이후 추가 지시들을 모두 포함}
```
- **프롬프트 전체**는 요약하지 말고 원문 그대로 기록하라. 작업 중 사람이 내린 추가 지시도 순서대로 로그로 남겨 마지막에 README에 붙인다. (작업 시작부터 `notes/prompt-log.md`에 누적 기록하는 방식을 권장.)

### 7-3. GitHub Pages 배포 (승인 후 실행)
1. 저장소를 Public으로 생성하고 `index.html`, `README.md`를 루트에 올린다.
2. Settings → Pages → Source를 **main 브랜치, `/ (root)` 폴더**로 지정.
3. 1~2분 뒤 `https://{GitHub계정}.github.io/kearney-hotspot-{조번호}-cafe` 로 열린다.
4. **배포 URL을 실제로 열어 확인**한다 (404면 Pages 설정·브랜치·루트 위치 점검). 확인 전에는 "완료"라고 보고하지 않는다.
5. 5분 안에 URL을 사람에게 알려 패들릿 업로드를 돕는다.
